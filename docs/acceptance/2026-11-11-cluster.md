# Live collaboration on several processes (2026-11-11)

Build under test: `feat/v2` packed with `npm pack` and installed into an isolated Strapi 5.61.1 host (`api::article.article` with a Magic Editor X field `body`).

## Setup

- PostgreSQL 16 on 127.0.0.1:5440, fresh database `mex_cluster` (`--reset`).
- 8 Strapi processes (`strapi start`, `NODE_ENV=production`) on ports 1491–1498, the size of Railway 2 replicas × pm2 4. The first process starts alone and creates the schema; the other seven start afterwards.
- A non-sticky round-robin TCP balancer on 1480: every new connection (HTTP request or WebSocket) goes to the next process.
- Random secrets per run (kept in memory), outbound network blocked in every process, synthetic admin `cluster-admin@example.test`.
- `collaboration.pollIntervalMs` 200.

Command: `node scripts/cluster-acceptance.mjs --app <host> --pg postgres://…/mex_cluster --reset --base 1480`

## Results

| Check                                                                                                           | Result                                                                     |
| --------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| Two clients on processes 1491 and 1492 type into the same paragraph and add blocks at the same time (30 rounds) | both converge to the same 13 blocks                                        |
| No concurrent edit lost                                                                                         | 60 of 60 markers present                                                   |
| Concurrent block inserts (A appends, B prepends)                                                                | all kept, in order                                                         |
| A third client joins through the balancer                                                                       | receives the merged state (13 blocks)                                      |
| Process 1491 is killed (SIGKILL) while client A edits; A reconnects through the balancer with its unsent edits  | all 10 edits made during the crash arrive at client B                      |
| Process 1491 restarts; a fresh client connects to it                                                            | sees the full room                                                         |
| All clients leave from different processes at the same time                                                     | exactly one automatic snapshot (version 1); snapshot leases unique per key |
| Room stored in the shared database                                                                              | 74 update rows, 3,254 bytes                                                |
| Process logs                                                                                                    | no Magic Editor X warnings or errors                                       |

9/9 checks passed (first run and final run on the final build).

Not covered by this run: time-bucket snapshots (`snapshotIntervalMinutes`, minimum 1 minute) — they use the same lease mechanism (`snap:<room>:t<bucket>`) as the session-end snapshots that were proven exactly-once here.
