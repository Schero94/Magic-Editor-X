# Magic Editor X 2.6.2 acceptance: moving column items keeps concurrent edits (2026-11-18)

Build under test: `fix/columns-concurrent-move` at 54bc30f (rebased onto main 09398e6 as 4b98064; main only changed dev dependencies, CI and docs, so `admin`, `server` and `shared` are identical), packed with `npm pack` (package version 2.6.0 until semantic-release decides 2.6.2) and installed from the tarball into an isolated acceptance host (installed `dist/server/index.js` compared byte for byte with the tarball).

Host: Strapi 5.62.0, Node 22.23.1, PostgreSQL 16 (own cluster, TCP only), own ports (SQLite 2810/2812, PostgreSQL 2811/2813, cluster 2850-2868), new random secrets, outgoing connections blocked (`block-egress.cjs`), synthetic data only (`*.example.test`).

## What changed

A Yjs type exists only once in a document and cannot be moved (Yjs 13.6.33 README, "Nest types"). Column items were nested in the column arrays, so moving one (fewer columns) deleted it and inserted a copy, and an edit made in the original at the same moment was lost. Schema 4 keeps the items of a columns block in an item store on the block entry and lets each column hold a placement list of item ids (AGENTS.md, Columns block > Collaboration). The stored JSON is unchanged.

Three further defects were found by the proofs below and fixed on the branch:

- The block menu ("Number of columns", spacing, alignment) did nothing while someone typed in the same columns block: a remote change re-creates the block and the open menu still called the old tool instance (browser move stress: 4 of 4 rounds without effect before the fix).
- Several people adding a column at once gave a block more than four columns; the live guard then refused every update to it and the edits sent with them were dropped (cluster proof: 983 of 2,273 markers lost).
- After a refused update, a render scheduled just before it showed the new, still empty document, and the next edit deleted every block of the field for everyone (cluster proof: seed blocks 0 / 6).
