# Live Preview and Magic Editor X (2.6 re-check)

Research record for roadmap item 4 (Live Preview inline editing), deferred in 2.5 on Strapi 5.61.1 and re-checked on Strapi **5.62.0** on 2026-11-17/18. It says what Strapi offers, what changed since 5.61.1, what Magic Editor X 2.6 ships and what stays impossible, with the source of every claim. The integration guide is [guides/live-preview.md](guides/live-preview.md).

## What changed from 5.61.1 to 5.62.0

Diff of `dist` of `@strapi/content-manager`, `@strapi/admin`, `@strapi/core` and `@strapi/utils` 5.61.1 against 5.62.0, preview files only:

- `InputPopover`: nested fields get a `ComponentProvider` level (`getComponentLevelFromPath`) and are disabled when their root attribute is a shared (non-localized) field (`useShouldLockNonLocalizedField`).
- `Preview.mjs`: initial errors with `getPublishValidationErrors` instead of a local `validateSync`.
- `fieldUtils`: new `getComponentLevelFromPath`.
- Unchanged: the preview script, `INTERNAL_EVENTS` / `PUBLIC_EVENTS`, the content source maps service (`ENCODABLE_TYPES` contains `json`, but only a value that is a string is encoded, so an object value of a JSON custom field is skipped), the exports of `@strapi/content-manager/strapi-admin` (still no preview hook; `usePreviewPopoverBlockIndex` is not exported).

After 5.62 (in `develop`, PR #28112, not in 5.62.0): the preview script keeps decoded sources in memory instead of writing `data-strapi-source` attributes; frontends that write the attribute themselves keep working.

## What the installed 5.62.0 code does (measured on the community edition host)

Host: Strapi 5.62.0 community edition (no license), SQLite, `config/admin.js` `preview: { enabled: true, config: { allowedOrigins, handler } }`, a synthetic front end on 127.0.0.1 that renders `?mex=html&mexBlockIds=true` with the header `strapi-encode-source-maps: true`. Chromium, 1440 x 900 and 390 x 844, light and dark.

- **Preview on the community edition**: the Preview page opens full screen; no side editor toggle (`hasAdvancedPreview = window.strapi.features.isEnabled('cms-advanced-preview')` gates only the side editor panel). The admin sends `strapiScript` after `previewReady`; the script highlights every element with a `data-strapi-source` attribute (the `@vercel/stega` import from cdn.jsdelivr.net was blocked in the test browser, so only explicit attributes were used).
- **Double-click on the community edition**: `InputPopover` is rendered unconditionally in `Preview.mjs` and handles `strapiFieldFocusIntent` without a license check. Double-clicking a Magic Editor X block opened Strapi's popover with the whole Magic Editor X field in it (4/4 viewport and theme runs), and typing there worked. The public docs list double-click editing as part of Live Preview (Growth/Enterprise, experimental); Magic Editor X does not rely on the popover and does not claim it as a feature. It is Strapi's UI: the popover is sized by Strapi and opens the field at its start, not at the clicked block (the block index lives in `usePreviewPopoverBlockIndex`, which is not exported).
- **`strapiFieldChange` and JSON fields**: on every change in the popover (and in the side editor) the admin posts `strapiFieldChange` with `{ field, value, type }`; for a Magic Editor X field `type` is `json` and `value` the whole Editor.js object. The preview script forwards only Strapi Blocks (`type === 'blocks'` or a Slate-like array) to the front end; for anything else it sets `textContent = String(value)` on every element whose source contains `path=<field>`. Measured: with `path=body` in `data-strapi-source`, the rendered blocks became "[object Object]" after one keystroke. Without a `path` key (only `fieldPath=body`) the script grouped the blocks into one highlight, opened the field on double-click (it turns `fieldPath` into `path` for the focus intent) and left the DOM alone. Magic Editor X therefore writes `fieldPath` only.
- **Live update of a Magic Editor X field**: the public `strapiFieldChange` message reaches the front end in the iframe (`window` `message` event, origin of the admin). A front end that re-renders the field with `renderHtml(value, ...)` updates while the editor types (measured in the popover on the community host). This is the front end's code, not Strapi's.

## What 2.6 ships

1. **Block source attributes** (renderer option `blockIds`, off by default; `?mex=html&mexBlockIds=true` for Content API output): `data-mex-block-id`, `data-mex-field-path` and, with entry metadata (or Strapi's `strapi-encode-source-maps: true` header on the Content API), `data-strapi-source` without `path`. Same output in HTML, React and Vue; ids, paths and source parts validated by strict patterns; default output byte-identical.
2. **Click-to-locate**, two transports that need no Strapi internals:
   - URL: `?mexField=<path>&mexBlock=<id>` on the edit view URL (`editViewUrl(...)` builds it). The field with that path starts (also when it waits for the viewport), scrolls the block into view and puts the caret into it; a block that no longer exists shows "This block is no longer in the field." Works on every plan and also outside the preview iframe ("Edit this block" links).
   - Message: `magic-editor-x:locate` posted by a frame embedded in the admin page (Strapi's preview iframe) to the admin window; a mounted field with that path shows the block and answers `magic-editor-x:located`, so the front end knows it does not need to navigate (`requestLocate(...)`). This is for the Live Preview side editor, where the edit form is mounted next to the preview. Messages from any other window (the page itself, popups, other tabs) are ignored.
3. **Guide** with a tested front-end example: preview protocol, block attributes, click-to-locate, live re-render on `strapiFieldChange`.

Measured on the 5.62.0 community host (Chromium, 1440/390, light/dark, 4 runs each): click on a block in the full-screen preview opened the edit view with the caret in that block, 19 blocks down a lazily started field, in 1.8 to 1.9 s; a `magic-editor-x:locate` message from an iframe placed in the edit view (stand-in for the side editor, which needs a license) put the caret into the block without navigation; a message posted by the page itself was ignored; a missing block id showed the notice; no horizontal overflow; 0 console messages from Magic Editor X. The real side editor was not tested (Growth/Enterprise license).

## What stays impossible, and why

- **Typing in the preview page itself** (contenteditable on the front end): Strapi has no API for a front end to send edits back; its only write paths are the Edit view form and its own popover. Not possible with public APIs.
- **Opening Strapi's popover at the clicked block**: the popover gets the block index from `usePreviewPopoverBlockIndex`, which is not exported from `@strapi/content-manager/strapi-admin` 5.62.0, and the focus intent that carries it is an `INTERNAL_EVENTS` message ("not part of the public API"). Magic Editor X does not listen to internal events.
- **Stega markers in Magic Editor X values**: `encodeSourceMaps` encodes only string values; a JSON custom field holds an object and is skipped (`content-source-maps.mjs`, unchanged in 5.62.0). There is no hook to encode a custom field. The block attributes replace this.
- **Live update without front-end code**: the preview script patches DOM text only for non-Blocks fields and forwards only Strapi Blocks; a Magic Editor X value must be re-rendered by the front end (guide).
- **Side editor and live sync on the community edition**: gated by `cms-advanced-preview` (Growth/Enterprise); not tested here.
- **Fields in collapsed repeatable components or dynamic zone entries**: the Content Manager does not mount them, so a locate request for `sections.0.body` does nothing until the entry is expanded (measured). Strapi's docs also say "Fields in dynamic zones are not handled" by Live Preview.
- **GraphQL**: Strapi adds source maps to REST responses only; `mexBlockIds` is a REST query parameter. GraphQL users pass `blockIds` to the renderer themselves.

## Triggers that reopen this

A public Strapi API for custom fields in preview (encoding hook, exported popover block index, a public focus-intent event), a `strapiFieldChange` path for JSON values, or Live Preview leaving experimental status with documented custom-field support.
