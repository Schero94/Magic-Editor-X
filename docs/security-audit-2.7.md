# Magic Editor X 2.7 security review: Core Blocks bridge

Scope: the Core Blocks bridge added in 2.7 on top of 2.6.2 (`main` at be6f397): the server registry
`service('core-blocks')`, the wrapper around Strapi's entity validator
(`server/src/utils/core-blocks-bridge.js`), the Settings switch (`PUT /settings` `coreBlocks`), the admin
helper `apis.addCoreBlocks` and the Settings section. Checked 2026-11-19 against Strapi 5.63.0 (acceptance
host, SQLite and PostgreSQL 14) and 5.38.0 (peer floor).

Background: Strapi's blocks validator (`@strapi/core` `services/entity-validator/blocks-validator`, the
same from 5.38 to 5.63) rejects every node type it does not know. The server-side fix is proposed in
[strapi/strapi discussion 25546](https://github.com/strapi/strapi/discussions/25546#discussioncomment-19718520).
The bridge is the plugin-side stopgap and turns itself off when Strapi supports custom blocks natively.

## Unchanged controls re-checked

No new admin or Content API route and no new permission action. The admin helper only forwards block
definitions to Strapi's `addRichTextBlocks` and keeps type names in memory for the Settings coverage
note; it sends nothing. The Settings section links to GitHub with `rel` set by the Design System link
(`isExternal`). `npm audit --omit=dev` is unchanged by 2.7 (no dependency added).

## Residual risk

- The bridge depends on an internal Strapi hook point. The canary and CI reduce, but cannot remove,
  the risk that a Strapi release changes behaviour in a way the canary does not cover. The bridge then
  fails closed (rejects) or stays out; it does not accept unvalidated nodes.
- A registered schema is the host's code; a permissive schema (for example `yup.mixed()`) accepts
  anything within the limits. Document review of registered schemas is the host's responsibility.
